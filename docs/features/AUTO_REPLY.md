# 自动回复功能说明

自动回复负责把平台上的一条客户消息，变成一次有记录、可判断、可确认的回复操作。
PC 配置机器人和账号，Core Nexus 决定回复内容，UCP 在操作员登录的平台环境中采集、发送并同步结果。
本说明介绍消息执行业务；角色、知识、规则与校准的详细配置见 [AI 客服说明](AI_CUSTOMER_SERVICE.md)。
客户端登录/租户、工作窗口与休眠、远端状态检查、日志操作和本地恢复，见 [UCP 日常操作指南](../../ucp/docs/OPERATIONS.md)。设备授权、后端对话导出与删除、清理后防历史回灌，见 [高级管理工具](ADMIN_TOOLS.md)。

## 谁使用这项功能

| 使用者 | 主要操作 |
| --- | --- |
| 管理员或运营人员 | 在 PC 新建评论/私信机器人，选择平台、运行参数和客服账号资料 |
| 客服配置人员 | 维护角色、业务知识、固定问答，测试回复及处理异常 |
| 桌面值守人员 | 在 UCP 登录后端与平台，启动机器人，观察授权、页面、发送和记录状态 |
| 开发人员 | 扩展平台控制器、接口、消息身份识别、确认和恢复逻辑 |

“自动回复”入口把私信和评论分成两个页签，二者可以使用不同机器人与设置。
代码入口：[PC 自动回复页面](../../kf-pc/src/views/customer-service/auto-reply/index.vue#L7)。

## 当前平台和渠道范围

| 平台与渠道 | 已有代码 | 上下文与发送方式 | 需要注意 |
| --- | --- | --- | --- |
| 抖音评论 | 扫描评论、选定目标、获取回复、编辑发送、记录同步 | 页面可见评论、楼中楼和已有记录；页面脚本操作回复框 | 依赖当前网页结构与登录状态，不等于读取平台全部评论 |
| 抖音私信 | 会话扫描、消息聚合、生成、分段发送、发送前检查及回显确认 | 页面会话与消息、本地/后端上下文；页面操作 | 会话切换、客户新消息、锁与确认失败都可能中止本轮 |
| 视频号评论 | 作品/评论读取、后端回复、发送、回显检查及记录 | 在已登录环境中使用平台接口与评论线程 | 接口成功而未看到匹配回显时保留待确认状态 |
| 视频号私信 | 消息采集与聚合、后端回复、逐条发送、本地与后端记录 | 已登录环境中的消息/发送接口 | 有发送前插话重算；不能直接等同抖音的逐段插话保护 |
| 快手、小红书等其他入口 | 仅有部分配置、平台名称或预留结构 | 界面入口已禁用，控制器也拒绝未实现的平台 | 不作为本版已经可用的自动回复平台 |

消息结构中保存类型或占位内容，不代表已经实现图片识别、语音理解或所有富媒体回复。
群聊相关代码分支也不等于经过完整验收的多平台群客服产品。

## 主要后端接口

| 接口 | 用途 |
| --- | --- |
| `POST /api/v1/auto-replies/comment/runtime-reply` | 评论正式运行的内容判断与回复生成 |
| `POST /api/v1/auto-replies/dm/runtime-reply` | 私信正式运行的内容判断与回复生成 |
| `GET /api/v1/auto-replies/robots/:robotId/settings/:module` | 读取机器人评论/私信配置 |
| `POST /api/v1/auto-replies/comment/records/sync` | 同步评论采集及处理结果 |
| `POST /api/v1/auto-replies/dm/conversations/sync` | 同步私信兼容会话记录 |
| `POST /api/v1/dialogue-records/dm/resolve-sync` | 归并并同步标准私信会话与消息 |

这些接口需要后端身份与相应权限，负责配置、生成和记录，不直接代替客户端发送。
接口对应见 [自动回复控制器](../../core-nexus/src/modules/auto-replies/auto-replies.controller.ts#L31) 与 [对话记录控制器](../../core-nexus/src/modules/dialogue-records/dialogue-records.controller.ts#L22)。

## 一台机器人需要配置什么

| 配置项 | 用途 | 不应混淆的地方 |
| --- | --- | --- |
| 租户与后端账号 | 决定机器人、资料与记录属于哪个工作空间 | 操作员登录后端不等于已经登录抖音或视频号 |
| 平台登录、授权与设备 | 确定在哪个账号、哪个本地运行环境操作 | 不是在普通新建表单里选择多媒体账号或直接填 authId/deviceId；需核对客户端及后端关联 |
| 机器人类型 | 评论或私信 | 主动私信任务属于另一类线索执行流程 |
| AI 绑定 | 选择 DeepSeek 客服路径，或 Coze 兼容路径 | 正常 DeepSeek 使用后台身份和知识，不直接继承旧提示词全部字段 |
| 账号资料 | 关联店铺、客服角色、渠道与业务知识 | 绑定资料必须属于当前租户并处于可用状态 |
| 评论回复范围 | 全部未回复评论，或只处理针对账号评论的回复 | “范围内”只是候选资格，不保证每条最终都会回复 |
| 评论回复数据集 | 可选的“评论→回复”导入表 | 它与知识库固定问答是两种不同的配置来源 |
| 私信首次回复与上下文 | 在高级兼容设置中配置首轮内容、是否带会话上下文 | 启用首次回复可能先走配置文本，不是每轮都请求模型 |

DeepSeek 绑定的账号资料还要关联启用的客服角色；缺失、停用或跨租户会被后端拒绝。
配置位置见 [机器人表单](../../kf-pc/src/views/robotmanagement/components/RobotFormDialog.vue#L43)；账号校验见 [客服通道服务](../../core-nexus/src/modules/customer-service-agent/runtime/channel/customer-service-channel-reply.service.ts#L92)。

### 评论回复数据集怎样维护

在评论机器人的“评论导入回复数据”管理弹窗中，可以新增、编辑、删除数据集，或导入自己的评论与回复表格。主要行字段为 `commentContent`、`replyContent`、`keywords`、`matchType`、`priority`、`enabled`，也接受对应中文表头。

数据集行支持精确、包含和模糊匹配；新行/导入默认精确。它与知识库 `FIXED_QA` 统一 FUZZY 的规则不同，不应把一种配置的匹配方式套用到另一种。

先核对表格内容和启用状态，保存数据集，再在目标机器人的评论配置中选择相应数据集。弹窗“回填样例”只写入表单，默认停用且不会自动保存。后端另提供单条匹配测试接口；这不代表弹窗已有独立完整的在线匹配测试工作台。

实现见 [数据集管理弹窗](../../kf-pc/src/views/robotmanagement/components/CommentReplyDatasetManagerDialog.vue#L48)、[导入与匹配接口](../../core-nexus/src/modules/auto-replies/auto-replies.controller.ts#L106)。

### 兼容提示词的应用与同步

旧提示词配置可以独立维护，再“应用到机器人”形成相应配置/快照；也可以将机器人的当前快照同步回配置项。这和维护正式客服角色、知识资产不是同一条配置链。

修改旧提示词配置后，不应仅凭编辑保存就推断全部机器人已经读取最新内容；需要核对应用/同步动作、客户端取得的配置和实际选择的运行路径。正常 DeepSeek 正式通道不直接继承旧 Coze 提示词全文，见本篇兼容路径说明。
接口见 [提示词应用与快照同步](../../core-nexus/src/modules/auto-replies/auto-replies.controller.ts#L82)。

## 一次评论回复怎样完成

1. UCP 读取当前作品和可见评论，识别顶层、回复层、作者、时间与已有回复。
2. 按机器人回复范围、已处理记录、页面状态等条件筛选候选。
3. 为当前目标准备线程上下文；可以来自本地记录、当前页面以及后端已有记录。
4. 将机器人、目标消息、作品上下文、线程标识和回复尝试标识发送到 Core。
5. 后端先尝试当前范围内的固定问答，再尝试已选择的评论回复数据集。
6. 两者未命中时，进入 DeepSeek 客服通道或配置的 Coze 兼容路径。
7. 后端返回“回复、跳过或需人工处理”的判断，以及回复文本、来源和追踪信息。
8. UCP 再检查目标与页面，执行回复操作，观察接口结果或页面回显。
9. 将生成、跳过、发送失败、发送成功或待确认等结果写入记录并同步。

固定问答和数据集命中都可以跳过模型，但它们的来源、适用范围与维护入口不同。
后端先后顺序见 [评论回复实现](../../core-nexus/src/modules/auto-replies/auto-replies.service.ts#L382)。

### 评论范围不是“无差别全回”

`ALL_UNREPLIED` 表示允许检查全部未回复候选；`PUBLISHER_REPLY_THREAD_ONLY` 限制为针对账号评论的回复。
已经有人工作答、已确认处理、状态不适合继续操作的目标，还会在客户端和记录查询阶段被过滤。
DeepSeek 评论通道还会结合当前评论、作品和账号背景判断是否值得自动回应。
不能把扫描到的评论数、进入候选数、生成数和实际发送成功数当成同一指标。

## 一次私信回复怎样完成

1. 识别当前会话、联系人和新收到的客户消息，合并属于同一轮的连续输入。
2. 读取可用历史，尽量保持本地会话、后端标准会话与旧工作流会话的对应关系。
3. 如果启用了首次回复，且客户端尚未把该会话认定为已完成首轮，可先使用配置内容。
4. 普通轮次提交当前消息、历史、消息 ID、会话 ID 和回复尝试 ID。
5. Core 处理准入判断、知识、生成与回复约束，返回一条或多条内容。
6. UCP 区分真正的“无需回复”和技术失败；失败不应被当成正常完成。
7. 发送前重新检查当前对象和客户最新消息，必要时取消旧草稿或重新聚合。
8. 执行发送并保存实际发出的内容，再同步后端会话、追踪及发送状态。

私信上下文不是无限记忆；输入窗口、会话归并、可用记录和后端状态都会影响本轮内容。
恢复出来的同名联系人仍可能需要身份判断，不能仅凭昵称保证是同一个客户。
主入口见 [UCP Core 服务](../../ucp/app/services/core_nexus_service.py#L234) 与 [抖音草稿生成](../../ucp/app/platforms/douyin/dm/draft/draft_runtime.py#L204)。

## 回复、跳过和转人工怎样区分

| 结果 | 当前实现含义 | 客户端应如何理解 |
| --- | --- | --- |
| `SEND` | 允许进入后续生成与交付流程 | 不代表已经发送，也不保证后续检查必定通过 |
| `SKIP` | 当前内容不自动回复 | 记录原因，避免把它算成技术故障 |
| `HANDOFF` | 本轮不自动回复，并返回需要人工处理的标记 | 不等于整个会话永久停机，也不等于已分配坐席或人工自动接入 |
| `replyStatus=failed` | 生成、接口或其他技术阶段失败 | 保留失败原因与重试/恢复条件，不能伪装成正常跳过 |

这三种决策在正式 DeepSeek 通道中有明确分工：

- 命中适用的固定问答时，先走确定性答案，不依赖评论准入模型。
- 评论未命中固定问答时，由准入模型判断相关性、询问价值、噪声、广告或风险。
- 评论准入模型不可用时，当前实现采取不自动回复的保守结果。
- 私信准入不另加一次通用模型审核，只拦截代码中明确的人身安全、法律升级和广告导流模式。
- 普通问候、商品问题、不满、售后问题和闲聊通常继续进入客服主流程；后续仍有事实、权限和交付检查。

这不是完整风险识别保证，字符串模式和模型判断都存在边界。
UCP 的兼容会话同步仍写入 `manualTakeover=False`，当前没有据此建立持久人工接管队列；需要人工处理的标记与真正的坐席工作流应分别理解。
具体分支见 [通道准入](../../core-nexus/src/modules/customer-service-agent/runtime/channel/customer-service-channel-reply.service.ts#L252)。

## 分段发送、首条回复与客户插话

账号后台可配置发送方式、最多消息数、段间等待和“客户插话时取消后续消息”。
这些是给运行时的配置，实际执行还取决于平台控制器。

| 场景 | 抖音私信 | 视频号私信 |
| --- | --- | --- |
| 多条回复 | 根据交付分段组织等待和发送 | 取后端 `replies`，逐条调用发送接口 |
| 生成期间客户补充消息 | 发送前检查与聚合逻辑参与判断 | 发送前再收集新消息，旧草稿可被取消并合并重算 |
| 后续段落前检查 | 检查会话对象、最新来信、会话锁；条件变化可取消剩余段 | 当前逐条发送循环未见同等的每段插话守卫 |
| 首次配置文本 | 可组织多段；群会话分支可能合并 | 按首次回复配置建立本轮回复列表 |

因此不能宣传“两个平台都能在任意段落被客户插话即时打断”。
抖音后续段会将 `delayBeforeMs` 限制在350–5000毫秒，不能假定任意后台等待值都会原样执行。
抖音实现见 [分段守卫](../../ucp/app/platforms/douyin/dm/send/send_runtime.py#L183)；视频号见 [发送前重算与发送循环](../../ucp/app/platforms/wechat_video/session_controller.py#L3988)。

## 确认发送与“待确认”

生成成功、点击发送、接口应答成功、页面出现回显，是不同层次的证据。

- 抖音私信会结合最新发出内容、可见气泡、会话摘要和输入框/发送按钮状态确认。
- 视频号评论在接口成功后再查找对应回复回显；未看到匹配回显时记录 `sent_unconfirmed`。
- 视频号私信当前把成功的平台接口应答作为本轮发送确认依据，记录中可见 `platform_api_ack`。
- 本地记录还区分 `send_pending`、`send_failed`、`send_unconfirmed`、`sent` 和后续确认等状态。

“待确认”不能直接算作未发送后重新发送，否则可能造成重复回复。
同样，后端生成记录存在也不能证明平台已经收到；排查时应同时看客户端发送证据。
实现见 [抖音发送确认](../../ucp/app/platforms/douyin/dm/send/send_runtime.py#L226)、[视频号评论确认](../../ucp/app/platforms/wechat_video/session_controller.py#L3205) 和 [本地状态定义](../../ucp/app/services/local_records/schema.py#L29)。

## 去重和恢复靠哪些记录

| 层次 | 保存什么 | 起什么作用 |
| --- | --- | --- |
| 运行内存 | 当前目标、会话锁、在途尝试、已处理消息、冷却与等待状态 | 减少同一轮并发和界面反复扫描导致的重复操作 |
| UCP 本地 SQLite | 会话、消息、分析、回复尝试、来源与确认状态 | 重启后仍有可查询的消息与发送线索 |
| 本地恢复文件 | 暂时无法入库的记录事件 | 可重放写入，失败记录进入恢复或隔离处理 |
| Core 评论/对话记录 | 目标、线程、回复状态、会话映射和已处理信息 | 跨扫描或客户端查询时参考已知状态 |
| Core 正式客服运行请求 | 进入客服 `runtime/replies` 契约的生成分支对应的幂等结果 | 在该契约内复用重复技术请求的结果，阻止同键不同消息 |

这些保护覆盖不同环节，不能推导为严格的“平台端恰好发送一次”。
固定问答直出、Coze 外部 Trace，以及进入正式运行服务之前返回的跳过/转人工分支，不一定保存相同的运行幂等结果，不能概括为所有 `runtime-reply` 请求都使用同一种持久化契约。
网络中断、页面变化、回显缺失和本地记录问题仍可能需要人工核对。
持久化实现见 [本地记录服务](../../ucp/app/services/local_records/service.py#L191) 和 [恢复重放](../../ucp/app/services/local_records/recovery.py#L41)。

## 正常 Core 路径与历史兼容路径

| 路径 | 配置与内容来源 | 使用前提 |
| --- | --- | --- |
| UCP → Core → DeepSeek 客服 | 后台账号资料、角色、知识与规则 | 后端模型凭据、启用的账号/角色及客户端绑定 |
| UCP → Core → Coze | 旧提示词快照、工作流/Bot 配置；部分场景允许异常回退 | 自己的 Coze 凭据、兼容工作流和正确输入输出结构 |
| UCP 本地兼容引擎 → Coze/静态兜底 | 本地历史配置、提示词及 fallback 文本 | 本地 Coze 默认关闭，需 `COZE_ENABLED=1` 且填写 `COZE_TOKEN`、`COZE_WORKFLOW_ID`；静态兜底按具体控制器处理 |

PC 的“高级兼容设置”和 `fallbackToCoze` 不等于所有错误都会自动重试 Coze。
UCP 的 `COZE_ENABLED` 只控制本地兼容引擎，不决定 Core 自己选择的 Coze 路径；两端要分别配置。
后端未允许回退时，DeepSeek 错误会继续作为失败处理；抖音已配置后端的私信错误也会保留技术失败，不直接换成本地固定句。
本地兼容引擎仍有静态/表情兜底代码，不能把它的输出当作后台知识生成已经成功。
本版没有附可导入的 Coze 云端资产，填一个 ID 不会自动创建工作流。
兼容参数分工见 [运行配置选择](../../ucp/app/services/auto_reply_runtime.py#L122)。

## 建议的配置和操作顺序

1. 完成自己的后端配置与初始化，用测试租户登录 PC，确认访问权限。
2. 先维护启用的客服角色、账号资料和最小业务知识；需要固定答复时单独配置固定问答。
3. 在“自动回复”选择评论或私信，新建机器人并选择平台和客服账号资料；普通表单没有直接选择授权/设备的字段。平台登录、授权和执行设备按客户端与后端关联流程建立后，再在 PC 核对回显，详见高级管理工具。
4. 设置评论范围、可选数据集，或私信上下文/首次回复等实际需要的选项。
5. 先在 PC 测试入口输入几条常见问题，检查来源、判断、回复及 Trace；测试不会代替平台发送验收。
6. 在 UCP 配置自己的 Core 地址，登录后端并获取对应机器人；再登录相应平台账号。
7. 检查平台授权、当前账号与页面后启动，先用专用测试对话/评论观察完整处理过程。
8. 同时查看 UCP 本地记录和 PC 回复记录；核对生成文本、实际发送、确认方式及同步结果。
9. 配置改动后发起新的测试消息确认生效；同一个幂等请求可能复用旧结果。
10. 遇到异常先停下该目标或机器人并核查状态，避免用反复点击启动代替发送确认。

## 在哪里看结果和排查失败

PC“回复记录”按私信对话和评论线程组织，便于查看消息与处理结果。
Reply Trace 记录后端为什么这样生成；UCP 记录具体有没有尝试发送及看到什么确认。
二者通过回复尝试 ID、消息/会话 ID、Trace ID 和来源字段关联。

| 现象 | 优先检查 |
| --- | --- |
| 机器人列表或账号资料不可用 | 当前租户、权限、机器人状态、账号/角色是否启用 |
| 无回复但没有报错 | 回复范围、已处理判断、`shouldReply`、`skipReason` 与人工处理标记 |
| 生成失败 | 模型/工作流配置、HTTP 失败原因、后端返回状态与客户端重试记录 |
| 有文本但没发出 | 当前会话/评论目标、页面元素、发送前检查、锁、是否被新消息取代 |
| 平台可能已经收到但记录未确认 | 平台回显、`sent_unconfirmed`、接口确认方式；先核对再决定是否重试 |
| PC 没看到最新记录 | 本地是否落盘、同步队列/接口是否失败、关联的机器人和租户是否一致 |

页面入口见 [PC 回复记录](../../kf-pc/src/views/customer-service/records/index.vue#L7)。

## 一个不包含真实客户信息的流程示例

假设你为“示例门店账号”配置了一条已经核实的营业时间固定问答。
客户评论询问营业时间时，Core 先按当前账号的知识适用关系查找固定问答。
命中后返回配置答案及来源；UCP 仍需要完成目标确认、发送和记录同步，不能因固定问答命中就记为发送成功。
客户私信补充“我问的是节假日”时，需要按新的消息和可用事实重新处理；没有节假日资料就不能自行承诺。
这个例子解释配置流转，不是实际客户案例，也没有预设模型措辞、响应时间或获客效果。

## 使用边界

- 本版已整理源码并完成部分构建/离线检查，没有在当前真实平台账号上完成全链路验收。
- 平台页面、登录、接口和风控变化可能使采集、发送或确认失败。
- `HANDOFF` 不提供完整人工坐席派单；消息状态也不是订单、成交或线索质量证明。
- 后端没有因此自动取得真实店铺订单、库存或物流权限，相关事实需要用户自己的可靠来源。
- 客服生成与平台执行分开排查；历史阶段记录或测试通过数不能当作真实业务效果。
