# AI 客服后台功能说明

AI 客服后台用于维护“以谁的身份、依据哪些事实、按什么规则回答，以及回答后怎样复盘”。
它不是单个提示词输入框，也不是直接操作抖音/视频号的发送程序。
PC 负责配置与查看，Core Nexus 负责运行、存储和追踪；平台采集与发送由 UCP 等客户端完成，见 [自动回复说明](AUTO_REPLY.md)。
首次启用还需区分系统模块定义同步、当前租户初始化和显式母版升级；Guideline、调优档案及评测接口的入口范围详见 [高级管理工具](ADMIN_TOOLS.md)。这些操作与管理员种子初始化不同。

## 谁使用、从哪里进入

| 使用者 | 主要工作 | PC 入口 |
| --- | --- | --- |
| 业务负责人 | 确认业务事实、权限、不能承诺的事项 | 账号配置、知识与流程 |
| 客服或运营配置人员 | 配角色、账号身份、知识、固定问答，测试常见场景 | 角色配置、账号配置、知识与流程、对话测试 |
| 调优人员 | 查看失败证据、提出校准、核实知识、检查新回复 | 回复记录、对话测试、校准沉淀、效果观察 |
| 有发布权限的管理员 | 控制共享策略与版本的正式生效、回滚和数据治理 | 资产版本、校准策略、数据治理等高级工具 |

菜单和操作按钮还受登录权限控制，页面存在不代表每个账号都能编辑或发布。
普通使用优先掌握角色、账号、知识与测试；角色原型、行业结构及高级资产可按需要维护。
菜单“测试与优化”进入的就是本篇所说的“对话测试”页面；不要再寻找另一个同名菜单。当前“知识与流程”把业务知识、客户意图与流程、固定回复与必走流程、表达限制组织成页签；“角色配置”包含默认角色/Prompt、其他角色和行业高级配置。旧入口和重定向关系见 [覆盖检查表](../FEATURE_COVERAGE.md)。
入口分工见 [角色配置](../../kf-pc/src/views/customer-service/role-center/index.vue#L3) 与 [知识与流程](../../kf-pc/src/views/customer-service/knowledge/index.vue#L3)。

## 后端接口按职责分开

客服专用 API 使用 `/api/v5/customer-service`，并按租户与权限处理请求。

| 路径组 | 作用 |
| --- | --- |
| `admin/context-profiles`、`admin/merchant-roles` | 账号/店铺背景及角色配置 |
| `admin/knowledge-entries` | 知识集合、适用绑定、导入、预览和固定问答解析 |
| `admin/simulations`、`admin/tuning-sessions` | 编译/执行测试及保存测试会话 |
| `admin/calibrations`、`admin/reply-traces` | 反馈、分析、应用、知识修订与回复证据 |
| `runtime/replies` | 正式运行的幂等回复契约；不直接操作外部客户渠道 |

接口见 [知识控制器](../../core-nexus/src/modules/customer-service-agent/admin/knowledge-entries/customer-service-knowledge-entries.controller.ts#L24) 和 [正式运行控制器](../../core-nexus/src/modules/customer-service-agent/runtime/reply/customer-service-runtime-reply.controller.ts#L13)。

## 几层配置分别管什么

| 配置层 | 放什么 | 不应放什么 |
| --- | --- | --- |
| 客服角色 | 共用的专业角色、稳定行为、默认生成 Prompt | 某天临时库存、未经核实的价格或某家店的独有事实 |
| 角色原型与行业节点 | 可复用的角色结构、行业共性能力 | 直接当成已证实的商家承诺 |
| 店铺/业务主体 | 主营业务、品牌介绍、规则、权限边界、时效说明 | 模型猜测出的客户订单或真实执行结果 |
| 账号资料 | 对外身份、所属店铺、使用角色、渠道和账号差异 | 在每个账号重复复制全部共用知识和角色 Prompt |
| 知识库 | 商品、服务、政策、FAQ、文档、结构化事实与引用 | 把一次模型建议直接当成已核实最高权威事实 |
| 固定问答 | 明确输入与固定答案、适用范围、排除条件 | 需要动态推理、实时查单或随时变化的结论 |
| 流程/响应规则 | 什么条件下需要哪些步骤、要点或确定性内容 | 只为了口语自然就堆积大量硬规则 |
| 表达限制 | 禁用某个词、符号、固定替换等确定性边界 | 取代角色正常语气与表达方式的全部控制 |

维护顺序应先把身份与事实讲清，再调整生成风格；只改语气不能弥补知识缺失。

## 角色、店铺和账号怎样关联

1. 先准备启用的客服角色，普通账号可以沿用系统推荐角色。
2. 建立店铺/业务主体，填写主营业务、介绍及已确认的规则。
3. 新建账号资料，选择使用角色、所属店铺和渠道。
4. 填写该账号对外身份；确需不同表达时才开启账号身份 Prompt 覆盖。
5. 保存为可用状态，机器人选择这份账号资料。

账号继承角色默认 Prompt；账号覆盖是差异化配置，不是第二份业务事实数据库。
同一家业务主体的多个渠道账号可以共享店铺知识，同时保留各自身份和渠道设置。
账号还可以继承店铺的回复长度、发送方式、段间等待和插话取消设置，也可按账号覆盖。
这些发送体验设置要由客户端执行，不能只看保存成功就认定各平台行为完全一致。
表单及说明见 [账号资料页面](../../kf-pc/src/views/customer-service/context-profiles/index.vue#L145)。

## 知识集合与“适用于谁”

知识集合用于把一批知识组织在一起，并明确这些知识对哪些对象可用。
当前界面在创建或编辑知识库时，同时选择店铺、客服身份或特定账号，可多选。

| 适用对象 | 适合的内容 | 后续账号怎样使用 |
| --- | --- | --- |
| 店铺 | 整家业务主体共享的商品、服务和政策 | 选择该店铺的账号按关系继承 |
| 客服角色 | 该角色可用的共性知识 | 使用该角色的账号按关系取得候选 |
| 特定账号 | 某渠道或某身份专属的内容 | 只在相应账号范围参与候选 |

正常流程是“建知识库并选择适用对象→维护知识”，不需要在机器人上再手工绑定每条知识。
已启用知识库必须有有效适用对象；草稿可以暂不配齐，未配置对象的旧库不会因此自动进入正式回复。
账号更换店铺或角色后，运行时按当前关系重新计算可用集合，不应继续假定旧知识一定可用。

“关系命中”和“内容检索命中”也不同：先确定哪些知识有资格进入候选，再按本轮问题检索相关内容。
知识和集合需要启用，且处于允许的生效时间范围；不能把归档、停用或过期知识当成必然会被使用。
知识预览可以帮助区分“没有适用候选”和“有候选但本轮问题没检索到”。
代码见 [知识库界面](../../kf-pc/src/views/customer-service/context-profiles/components/BusinessKnowledgePanel.vue#L5) 与 [运行候选筛选](../../core-nexus/src/modules/customer-service-agent/infrastructure/persistence/customer-service-knowledge-entry.repository.ts#L30)。

## 常规知识可以维护哪些信息

| 信息 | 用途 |
| --- | --- |
| 标题、分类、常见问法、正文 | 让业务人员维护可读知识，并用于本轮相关性检索 |
| 实体类型、实体键、别名、标签 | 区分具体商品/服务及其不同叫法，减少对象混淆 |
| 结构化字段 | 明确存放商品属性、服务条件等可解析数据 |
| 来源说明与权威类型 | 标明内容来自哪里，作为事实、规则还是参考材料使用 |
| 生效/失效时间与时效说明 | 标记活动、政策等内容的适用时间及更新要求 |
| 可分享引用 | 保存知识相关的可用引用信息，不等于后端自动抓取网页并核实全文 |

页面支持手工维护与 Excel 导入；常规知识和固定问答使用不同入口。
常规知识导入会拒绝混入 `FIXED_QA` 或 `fixedQa` 结构，避免把确定性答案偷偷当作普通检索材料。
模板和示例用于说明填写格式，正式使用前需要替换成自己的可核实内容。
常规知识会被检索、组织并约束模型回答，不要求每轮逐字照抄，也不保证所有已启用条目都会进入上下文。

## 常规 FAQ 与固定问答有什么不同

| 维度 | 常规 FAQ/知识 | 固定问答 `FIXED_QA` |
| --- | --- | --- |
| 目的 | 提供事实、背景和可参考的处理方法 | 命中后返回事先确定的答案 |
| 生成方式 | 可参与模型组织和解释 | 本地确定性匹配，不用模型改写答案 |
| 匹配输入 | 常见问法、正文、实体等检索信号 | 触发问法与排除词等固定配置 |
| 未命中 | 继续其他知识与正常客服流程 | 不把未命中的固定答案偷放进普通知识生成 |
| 适用范围 | 当前账号/店铺/角色关系及有效状态 | 同样先受适用范围约束，再匹配输入 |

当前固定直出统一采用 `FUZZY` 模糊匹配；历史 EXACT、CONTAINS 等元数据不再决定运行匹配模式。
这里的“模糊”是代码内的文本相似度规则，不是让模型任意理解后直接选一句答案。
排除词可使某条答案不参与命中；多个候选还会比较适用具体程度、优先级和匹配情况。
不要将界面显示的相似度当作业务事实正确率或实际客户满意度。

固定问答可逐条创建，也可导入“输入→输出”Excel，一行生成一条；导入前需确认知识集合与范围。
命中后按配置返回固定答案，可按所设范围随机等待；这不是模型思考时间，也不保证各平台发送用时。
客户端仍可能做空白、长度或平台适配处理，“原文直出”主要指不再经模型改写。
固定匹配实现见 [固定问答解析器](../../core-nexus/src/modules/customer-service-agent/shared/context/customer-service-fixed-qa.util.ts#L46)。

## 客户意图、处理流程和确定性回复

“客户意图与流程”用于描述客户要办什么，以及该场景需要哪些信息和步骤。
识别出的候选可被业务人员查看和整理为定义，不是每条新说法都自动创建一套正式流程。

“固定回复与必走流程”是另一组高级能力：先维护响应资产，再建立触发条件。

| 响应资产 | 当前用途 |
| --- | --- |
| `EXACT_REPLY` | 要求使用确定的全文 |
| `TEMPLATE_REPLY` | 以已配置模板组织回复 |
| `REQUIRED_POINTS` | 要求回复包含指定要点 |
| `REQUIRED_WORKFLOW` | 要求遵循特定步骤或流程 |

触发条件可结合账号、场景、意图和风险等信息；运行只读取可用规则及正式发布的对应资产版本。
它们不同于输入相似度命中的固定问答，也不同于作为事实来源的普通知识。
角色 Prompt 负责表达方向，表达限制负责明确禁用或替换；不要把三层配置混成一张话术表。
现有类型见 [资产类型定义](../../core-nexus/src/modules/customer-service-agent/shared/constants/customer-service-foundation.constant.ts#L14)。

## 对话测试与仿真能检查什么

1. 选择角色和必要账号背景，开启独立测试对话。
2. 输入客户的自然说法，而不只测试一条事先写好的标准问题。
3. 查看理解结果、命中知识、约束、候选回复、质量和执行诊断。
4. 接受候选加入测试会话，或拒绝并发起校准，再继续追问。
5. 用改写、补充、否定、换话题等后续轮次检查上下文行为。

页面的“接受并发送”是写入测试对话，不等于直接向真实平台客户发送消息。
切换客服角色会开启新测试对话，保留原会话，避免两个身份共用一段历史。
部分 Robot Test 私信路径还单独维护测试会话状态，不把测试消息直接当作生产标准会话。

仿真可以暴露配置关系和生成问题，但不能证明平台发送、真实库存、真实订单动作或业务效果。
界面有评测与回归工具；历史验证记录、分数和“通过”标签只在各自测试范围内有意义。
页面见 [对话测试](../../kf-pc/src/views/customer-service/simulation/index.vue#L165)；测试回复写入见 [接受候选](../../kf-pc/src/views/customer-service/simulation/index.vue#L832)。

## 校准如何从反馈变成可用配置

校准记录保存原客户消息、原回复、反馈、配置与运行证据，再由分析器提出诊断、建议回复及抽象调整方向。
同一记录可以继续提出意见，保留多轮分析；管理员可选择其中适合的一轮应用，不必只用最后一轮。
不能把“模型分析完成”“建议回复好看”“已经点击应用”都当成同一种生效结果。

| 操作或范围 | 实际结果 | 后续要求 |
| --- | --- | --- |
| 仅生成分析 | 留下诊断、建议和草稿 | 尚未自动改变生产知识或规则 |
| 替换当前测试消息 | 使用所选建议更新符合条件的测试回复 | 不代表长期配置已发布，也不会自动改真实平台消息 |
| `ACCOUNT_*` / `ROBOT_*` 精确作用域应用 | 经授权人员确认后创建/更新 ACTIVE 校准档案 | 后续匹配此账号/机器人和范围的新生成可继承，不自动扩大到全角色 |
| `ROLE_*` 共享作用域 | 保存共享策略候选，默认不直接启用 | 需要策略草稿、满足回归条件及人工发布 |
| 意图识别误判 | 保留诊断证据 | 后端拒绝自动当作长期表达规则应用 |

精确作用域还区分当前上下文、场景和全局等范围；不是每次都影响该账号的所有消息。
已生效校准切换历史分析轮次时，后端要求保持原作用域；要改变范围应另建记录。
同一精确作用域的后续校准会合并抽象原则并处理修正，不能理解为把建议回复每次原样粘贴。
扩大账号来源的校准到角色范围还需要发布权限及影响范围确认。
真实判断见 [应用校准服务](../../core-nexus/src/modules/customer-service-agent/admin/calibrations/customer-service-calibrations.service.ts#L681) 和 [立即生效范围](../../core-nexus/src/modules/customer-service-agent/shared/calibration/customer-service-calibration-profile.util.ts#L310)。

### 把校准内容沉淀成知识

页面提供常规知识/固定答案等显式沉淀入口，维护者要选择内容、类型和适用范围。
常规校准样本可作为参考材料，不会因为来自模型分析就自动升级为已确认业务事实。
若问题是事实错误，更适合使用独立的知识修订草稿流程：

1. 从校准记录建立待核实草稿，选择当前账号或店铺范围，以及新增/修改哪条知识。
2. 由业务人员核对商品、制度、订单或负责人提供的事实，填写核实说明。
3. 草稿变为已核实后，再单独确认发布为正式启用知识。
4. 原知识已被别人修改时，后端检查修订版本，要求重新核对，避免覆盖新事实。
5. 用后续新回复的 Trace 验证是否真正命中，而不是只看发布提示。

事实草稿的人工核实是业务确认记录，不是系统自动替你完成事实调查。
流程见 [知识修订发布](../../core-nexus/src/modules/customer-service-agent/admin/calibrations/customer-service-calibrations.service.ts#L959)。

## 版本与逐轮生效边界

资产和 Guideline 有草稿、发布、历史版本与回滚入口；草稿保存不会自动替换正式版本。
校准生成的共享策略草稿，还要通过对应版本的回归，才能发布；正式运行接口拒绝直接加载未发布策略草稿。
角色、账号、知识等资料还记录 revision，更新时可能因并发版本不一致而要求刷新。
这些机制不等于每类资料都有相同的历史版本管理界面。

新的有效运行请求会按当前身份加载启用知识、规则、校准及正式策略，并记录来源版本。
已经生成的回复不会因后台修改被追溯改写；相同幂等键的成功请求会返回先前保存的结果。
因此验证新配置要使用新的客户消息/测试请求，并核对配置指纹、命中知识和版本，而不是重复点击同一旧请求。
旧 Coze 提示词快照、客户端首次回复文本也有自己的同步/读取方式，不属于同一个实时资产加载链。
版本入口见 [资产发布与回滚](../../core-nexus/src/modules/customer-service-agent/admin/assets/customer-service-assets.service.ts#L149)；逐轮读取见 [运行来源加载](../../core-nexus/src/modules/customer-service-agent/runtime/simulation/customer-service-simulation.service.ts#L877)；幂等边界见 [正式回复请求](../../core-nexus/src/modules/customer-service-agent/runtime/reply/customer-service-runtime-reply.service.ts#L91)。

## Reply Trace、质量和效果观察

| 记录 | 能帮助回答的问题 | 不能直接证明的事情 |
| --- | --- | --- |
| Reply Trace | 哪条消息、哪个账号、用什么配置和知识，为什么这样生成 | 真实平台一定已发送、客户一定已阅读 |
| 质量/安全状态及诊断 | 哪些约束、事实支持、候选或交付检查出现问题 | 人工服务质量、全部事实永远正确 |
| 客户端发送记录 | 有没有尝试发送、发送了什么、依据什么确认 | 后端这次一定用了最新知识 |
| 反馈与校准记录 | 谁提出了什么问题、如何分析和应用 | 自动提高成交或客户满意度 |
| 效果观察 | 按账号与时间窗口查看追踪、策略/知识变化相关的样本 | 排除其他因素后的因果效果 |

部分界面会展示模型、理解、事实引用、候选选择、分段、配置指纹和来源 revision；具体字段取决于运行分支和保存情况。
没有可关联 Trace 的人工/外部回复，不能按同等证据执行精确校准；页面会限制相应操作。
质量规则当前有查询接口，不能据此宣称所有质量项都有完整的可视化编辑能力。
质量拒绝可能清空可发送候选；失败内容供调优，不应当作已经交付给客户的回答。
实现见 [Trace 保存](../../core-nexus/src/modules/customer-service-agent/admin/reply-traces/customer-service-reply-traces.service.ts#L95) 与 [质量面板](../../kf-pc/src/views/customer-service/simulation/components/SimulationGenerationQualityPanel.vue#L45)。

## 数据保留与治理

后端对调优、校准、Trace 和过期幂等请求提供治理运行记录，并有 JSON 体积及保留参数。
治理模式包含预估、归档、压缩、清理和校验；预估会登记治理记录，但不等于已经删除业务数据。
清理默认关闭，需要显式开关及确认文本；并会检查相关记录是否仍被校准或反馈引用。
归档、压缩、删除测试会话和清理运行追踪是不同操作，不能当成一键无差别清空。
实际保留天数、批量和清理开关应按自己的业务与环境配置，不能保证所有数据自动按时间到期消失。
依据见 [数据治理服务](../../core-nexus/src/modules/customer-service-agent/admin/data-governance/customer-service-data-governance.service.ts#L61)；参数见 [后端配置说明](../../core-nexus/docs/CONFIGURATION.md)。

## 一个配置和复盘示例

以下是虚构配置演示，不是客户案例或效果承诺。
为“示例门店”建立店铺和咨询账号，选择“门店顾问”角色，再建仅适用于该店铺的知识库。
把已经核实的服务范围放常规知识，把适合固定答复的常见问题放独立固定问答。
在测试中输入常见问题，再补充一个没有资料的新条件，观察系统使用哪些知识、是否越界承诺。
如果只是语气冗长，可在当前账号精确范围校准；如果服务范围写错，应核实并修改事实知识。
改完用新测试消息检查 Trace；最后才在自己的平台测试账号验证采集、生成、发送与同步。

## 建议的首次使用顺序与当前不足

1. 确认租户、权限、模型配置和初始化状态。
2. 启用角色，建立店铺及账号资料，再设置知识库适用对象。
3. 导入少量已核实常规知识和必要固定问答，预览是否有可用候选。
4. 用多轮测试检查已知问题、未知条件、追问、否定和换话题。
5. 对问题分类：事实改知识，表达作精确校准，共享变更走回归发布，识别机制问题交开发排查。
6. 绑定机器人并使用测试账号验收真实平台流程，持续对照客户端记录和 Trace。

当前源码没有替你取得真实店铺查单、库存或物流权限；没有完整人工坐席派单系统。
模型、检索、语义检查及文本匹配都可能出错，启用知识也不保证每轮一定检索到。
本版构建和部分离线检查不代表客服效果、平台全链路或共享策略泛化已经验收；历史冻结记录也不能代替当前验证。
